# 记忆系统 Plan 1.0

## 1. 目标与依据

依据 [spec_1_0.md](../specs/spec_1_0.md) 制定从现有项目骨架到可运行终端记忆系统的开发路线图，覆盖实体维护、语义追加存储、记忆 Agent、主 Agent 及完整验收。

- 需求来源：[draft_1_0.md](../drafts/draft_1_0.md)。实现以 Spec 为准，包含其最新变更 `spec_1_0_1` 中的充分证据原则及关键词查询限制。
- 本 Plan 只安排任务、顺序、依赖和交付检查；业务规则、数据格式和接口以 Spec 对应章节为准。
- 沿用 Spec 第 2.3 节标注的 A1—A7 假设，不将其改写为新增的用户确认。
- 开发范围遵循 Spec 第 2 节，不引入持久记忆召回、额外服务、全局事务或自动数据迁移。
- 当前状态：**待实施**。本文生成仅完成规划，不代表下列实现或验收已经完成。

## 5. 执行顺序与依赖

主顺序为 **P1 → P2/P3 → P4 → P5 → P6**。

1. 先完成 P1 的契约，避免实体工具、语义工具和 Agent 分别定义不一致的结果格式。
2. P2 与 P3 的基础工作可并行：P3-1 向量化封装和 P3-2 集合检查不依赖实体实现；P3-3 的语义工具集成必须等 P2 可校验真实实体后进行。
3. P4 的工具执行链路依赖 P2、P3 的有效结果；创建返回真实 ID 后才能建立引用，相关实体和关系变更成功后才能保存依赖它们的语义。
4. P5 在记忆处理状态稳定后集成，P6 汇总全链路验收。单模块错误路径随阶段开发检查，不集中拖到 P6 才处理。
5. 指定模型的访问和工具能力可在 P1 核对接口后提前做最小联调，尽早暴露外部阻塞；提取行为和完整业务场景仍在 P4—P6 验证。外部服务受阻时，可继续独立的本地实现与受控验证，但不能标记真实模型验收通过。

### 6.2 验证执行方式

1. 优先运行实施时仓库已有的检查机制；当前未配置测试、Lint 和类型检查，不以本计划为由新增相关依赖或测试文件。
2. 使用临时工作目录中的 `.memory/`，通过直接函数调用、命令行片段和受控交互检查实际文件及数据库。验证数据与用户已有记忆隔离，不使用清空真实数据的方式准备环境。
3. 对 I/O、模型和写入超时等错误采用进程内受控替身或故障注入，检查批次前置校验、部分成功、未知结果和依赖中止；不创建或修改测试文件。
4. 真实模型联调使用 Spec 指定模型及系统环境凭据；记录实际成功与失败，不记录密钥。外部模型不可用时记录具体阻塞，不静默替换模型。
5. 除 AC 编号场景外，按 Spec §3—6 检查 UTF-8 字节上限、完整事实拆分、单事实超限、非法或非有限向量、空查询、损坏 JSON、文件名不一致、符号链接、循环上限、上下文超限及正常/异常资源关闭。
6. 重点检查关系仅一端写入成功时依赖语义停止，而其他独立明确内容仍可继续；历史回顾不覆盖当前状态，明确纠正更新当前结构并追加语义；助手回复或工具结果不自动成为用户事实。

## 7. 风险与处理顺序

| 风险或约束 | 发现时机 | 实施安排 |
| --- | --- | --- |
| 指定模型不可访问、工具调用不可用或 SDK 接口不兼容 | P1 接口核对及尽早进行的最小联调 | 按 Spec 报告具体错误；独立本地工作继续；如必须改变模型或技术设计，先反馈影响并取得用户确认，再调整 Spec 与 Plan |
| 已有集合缺少必要参数或格式不兼容 | P3 集合检查 | 保留原数据库并返回差异；不将自动迁移或重建加入本次实施 |
| 多文件关系更新或跨存储操作部分成功 | P2、P3 的错误路径验证，P4 集成 | 保留已成功数据，准确汇总逐项结果并中止依赖失败步骤的操作；不承诺全局事务 |
| 模型格式正确但证据判断不充分 | P4 受控流程与真实场景联调 | 分别验证格式约束与证据判断，重点覆盖同名、推测、混合确定性和历史关系；修正实现不能改变 Spec 的舍弃原则 |
| 缺少已有自动化测试套件 | 各阶段及 P6 | 用直接调用、隔离数据和受控交互提供可复现证据；不擅自新增测试文件 |

若实施中发现 Spec 存在关键歧义、冲突或必须改变既定需求与技术设计，暂停受影响任务，向用户说明影响和建议；确认并更新 Spec 后再同步本 Plan。单纯任务顺序或依赖调整可在不改变 Spec 的前提下更新计划并记录。
